# A shared kernel for cross-module IDs

Modules refer to each other only by ID (ADR-0003), so an entity's ID is the one part of a module that other modules depend on. Every entity's ID is a strongly-typed value object (`AccountId`, `MerchantId`, `ProductId`, generated by Vogen as a `readonly partial struct` over a version-7 `Guid`), and these ID types live together in a `SharedKernel` namespace inside `MicroCommerce.ApiService` rather than in the module that owns the entity. A module can then hold another module's ID (an Order's `MerchantId`, a Listing's `ProductId`) without referencing anything else in that module, and the compiler stops one kind of ID being passed where another is expected.

The shared kernel holds IDs only. Value objects with rules that matter to one module, such as `ShopName`, stay in that module's namespace. They are `public` only so the module's HTTP responses can carry them, and no other module refers to them.

## Considered Options

- **Raw `Guid` IDs**: rejected; nothing stops a `MerchantId` being passed as an `AccountId`, and the mix-up only shows up at runtime.
- **Each ID in its owning module's namespace**: rejected; a module holding another's ID would then reference that module's namespace, which is the coupling ADR-0003 rules out.
- **A separate SharedKernel project**: deferred; one namespace in the API project is enough while the modules share one process, and it moves into its own assembly when a module is extracted.

## Consequences

IDs serialise as plain UUID strings in JSON and appear in the OpenAPI document as `string`/`uuid`, so HTTP clients see no change. They are stored as `uuid` columns through EF Core value converters, so the database schema doesn't change. Keep the shared kernel small: anything added to it becomes a contract every module depends on.
